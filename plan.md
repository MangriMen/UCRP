# Plan: промпт для проектирования «Единой рекомендательной клиентской платформы для ТЦ»

Версия 2. Входные файлы лежат рядом: `case.txt` (кейс), `analysis.md` (анализ команды Good Enough, сконвертирован из `analysis.pdf`).

Что изменено относительно v1:
- промпт привязан к кейсу: предметная область, роли, сущности, US-1…US-11, сегменты, метрики взяты из `analysis.md`, а не оставлены плейсхолдерами;
- выбран frontend: **React** (обоснование ниже);
- зафиксированы допущения по неоднозначностям кейса (см. п. 0.3);
- убраны разделы, избыточные для хакатона (юридика, согласия, полноценная лояльность), и добавлены разделы, специфичные для кейса (склейка профилей, импорт, скоринг рекомендаций);
- прежние сквозные правила (единые ID, формат Mermaid, фазы, трассируемость) сохранены.

## Выбор frontend: React

| Критерий | React | Vue | Solid |
|---|---|---|---|
| Экосистема под админку (таблицы, формы, графики, drag-n-drop конструктор правил) | лучшая: TanStack Table/Query, React Hook Form, Recharts, shadcn/ui | хорошая: Vuetify/PrimeVue, Pinia | мала, часть компонентов писать самим |
| Скорость старта за хакатон | высокая | высокая | средняя |
| Доступность примеров/ответов LLM | максимальная | высокая | низкая |
| Риск | перерисовки в больших таблицах (решается виртуализацией) | — | узкая экосистема |

Решение: **React + Vite + TanStack Query + TanStack Table + React Hook Form + React Router**, JS (JSX). Vue — разумная замена, если команда лучше знает его; Solid не брать из-за экосистемы. Продукт — B2B-админка с таблицами ошибок импорта, очередью склеек и конструктором сегмента: именно там экосистема React даёт больше всего готового.

## Промпт (копировать целиком)

### 0. Входные данные

**0.1. Источники.** Прочитай `case.txt` и `analysis.md` целиком до начала работы. Это единственный источник требований; ничего не противоречащего им не придумывай.

**0.2. Суть продукта (кратко).** Агрегатор данных арендаторов ТЦ (CRM/PMS, касса/POS, API, Excel/CSV) → единый профиль Гостя + лента событий → динамические сегменты («был в A и B, не был в C») → рекомендации следующего места → выгрузка сегмента в канал рассылки (CSV и API; SMS/пуш/email). Продукт B2B2C: платит и решает УК, пользуется маркетолог, выгоду получает посетитель.

**0.3. Допущения (принять и вынести в раздел «Допущения»; не спрашивать заказчика заново).**
- Согласия на обмен и обработку данных между партнёрами есть; юридический конструкт, оформление согласий и полноценная лояльность вне scope.
- Форматы источников: берём 4 из `analysis.md` (CRM/PMS, касса/POS, API, Excel/CSV); минимум 3 из `case.txt` перекрыт.
- «Проект» из перечня событий (В-4) = объект данных/направление бизнеса арендатора (атрибут `project` события); справочник `Project`, привязан к арендатору.
- Событие имеет уникальный внешний номер операции (чек/бронь) для идемпотентности (В-5); повторная загрузка файла не создаёт дублей.
- Автосклейка только по надёжным ключам: телефон, email, номер карты. Спорные — в очередь на ручное подтверждение; склейка всегда обратима; вручную разъединённые профили не склеиваются повторно.
- Конверсия = визит в течение 14 дней после контакта; нужна контрольная группа без рассылки.
- Масштаб: 80–150 арендаторов, ~40 000 посетителей в месяц, файл до 100 тыс. строк; цифры примерные.
- Внешние каналы рассылки (SMS/пуш/email-провайдеры) вне системы: мы отдаём CSV и API, сами не отправляем.

**0.4. Стек.**
- **Backend:** Go, слои `handler → service → repository`, интерфейсы на границах, REST, горутины для импорта и пересчёта сегментов (воркеры + очередь).
- **Frontend:** React (JS) SPA, общение с backend только через REST.
- **БД:** SQLite на старте, миграция на PostgreSQL без переделки модели; 3НФ; миграции goose.
- **Принципы:** SOLID, чистая архитектура, слабая связность, расширяемость через справочники и контракты.

### 0.5. Ограничение: код приложения сейчас не пишем

На этом этапе результат — только аналитическая документация (текст, таблицы, диаграммы Mermaid). Не писать и не генерировать код приложения: ни Go, ни React/JS, ни тесты, ни конфиги, ни скаффолдинг проекта.
Допустимы только артефакты проектирования, которые требует п. 4: SQL DDL и миграции (как часть ER), OpenAPI/JSON-схемы контрактов, деревья каталогов Go-пакетов и React-модулей, сигнатуры интерфейсов на диаграммах классов. Реализацию начинать только по отдельной команде после согласования документации.

### 0.6. Режим работы: автономно до конца

- Выполни все фазы A→E подряд, без остановок и без вопросов по ходу работы. Не жди подтверждений между фазами; чекпойнты ведутся в файлах, а не диалогом.
- Неясность разрешай разумным допущением (приоритет: `case.txt` → `analysis.md` → п. 0.3 → лучшая практика), запиши его и иди дальше.
- Каждый артефакт сохраняй в файл `docs/` (см. «Рекомендации по запуску»); в чат выводи только краткий статус.
- Веди `docs/00-open-questions.md` с двумя списками, которые заполняются по ходу работы:

  2. **Спорные решения** — места, где было ≥ 2 разумных варианта (формат: ID `D-n`, варианты, выбранный, обоснование, цена отката).

### 2. Предзаданные идентификаторы (использовать без переименования)

**Роли `R-*`:**

**Сущности `E-*`:**

### 3. Сквозные правила

1. **Единые идентификаторы** (`R-*`, `E-*`, `UC-*`, `US-*`, `C-*`, эндпоинты `METHOD /path`); объект везде называется одинаково (глоссарий: русское имя + имя в коде).
2. **Привязка к стеку.** Под каждой диаграммой — таблица «элемент → Go-пакет/слой → React-модуль/компонент → API-контракт (метод, путь, ключевые поля)». Полные JSON-схемы — в приложении.
3. **Mermaid** в блоках ```mermaid. К каждой диаграмме 3–7 предложений пояснений. Для swimlanes — `subgraph`; для object diagram — `classDiagram` с экземплярами; оговорить ограничение.
4. **Диаграммы не перегружать:** ≤ ~15 узлов, иначе разбить.
5. **Изоляция арендатора** (R-3): во всех артефактах (CRUD, sequence, API, C4) явно показать, что арендатор видит только свои агрегаты и не имеет доступа к данным других арендаторов ни в UI, ни через API (проверка на уровне service + фильтр в repository).
6. **Идемпотентность и обратимость:** повторная загрузка не дублирует события; склейка и разъединение отражены в аудите.
