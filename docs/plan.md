## Выбор frontend: React

| Критерий                                                                         | React                                                              | Vue                              | Solid                                |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------- | ------------------------------------ |
| Экосистема под админку (таблицы, формы, графики, drag-n-drop конструктор правил) | лучшая: TanStack Table/Query, React Hook Form, Recharts, shadcn/ui | хорошая: Vuetify/PrimeVue, Pinia | мала, часть компонентов писать самим |
| Скорость старта за хакатон                                                       | высокая                                                            | высокая                          | средняя                              |
| Доступность примеров/ответов LLM                                                 | максимальная                                                       | высокая                          | низкая                               |
| Риск                                                                             | перерисовки в больших таблицах (решается виртуализацией)           | —                                | узкая экосистема                     |

Решение: **React + Vite + TypeScript + TanStack Query + TanStack Table + React Hook Form (+ zod) + React Router + Tailwind/shadcn**, тесты Vitest, линтер oxlint (версии в `apps/web/package.json`). Vue — разумная замена, если команда лучше знает его; Solid не брать из-за экосистемы. Продукт — B2B-админка с таблицами ошибок импорта, очередью склеек и конструктором сегмента: именно там экосистема React даёт больше всего готового.

## Промпт (копировать целиком)

### 0. Входные данные

**0.1. Источники.** Прочитай `case.txt` и `analysis.md` целиком до начала работы. Это единственный источник требований; ничего не противоречащего им не придумывай.

**0.2. Суть продукта (кратко).** Агрегатор данных арендаторов ТЦ (CRM/PMS, касса/POS, API, Excel/CSV) → единый профиль Гостя + лента событий → динамические сегменты («был в A и B, не был в C») → рекомендации следующего места → выгрузка сегмента в канал рассылки (CSV и API; SMS/пуш/email). Продукт B2B2C: платит и решает УК, пользуется маркетолог, выгоду получает посетитель.

**0.3. Допущения (принять и вынести в раздел «Допущения»; не спрашивать заказчика заново).**
Полный актуальный список — `docs/01-summary-assumptions.md` (A-1…A-23). Ниже — те, что отличаются от v2 или важны для промпта.

- Согласия на обмен и обработку данных между партнёрами есть; юридический конструкт, оформление согласий и полноценная лояльность вне scope.
- Форматы источников: 4 из `analysis.md` (CRM/PMS, касса/POS, API, Excel/CSV); минимум 3 из `case.txt` перекрыт. Заказчик не различает CSV и XLSX и не требует интеграции с конкретными системами: важна унификация в общий шаблон (FAQ В-2).
- «Проект» из перечня событий (В-4) = объект данных/направление бизнеса арендатора (атрибут `project` события); справочник `Project`, привязан к арендатору.
- Событие имеет уникальный внешний номер операции (чек/бронь) для идемпотентности (В-5); повторная загрузка файла не создаёт дублей.
- Автосклейка только по надёжным ключам: телефон, email, номер карты; телефон — базовый ключ MVP. Нужно показывать степень уверенности в склейке (FAQ В-1). Спорные — в очередь на ручное подтверждение; склейка всегда обратима; вручную разъединённые профили не склеиваются повторно.
- Посещение — подтверждённое бизнес-событие. Различаются `top_up` (пополнение), `usage` (списание) и визит; возврат/отмена аннулируют событие; отсутствие записи не доказывает отсутствие визита (FAQ В-3).
- Главная метрика — первая покупка гостя у нового для него арендатора/проекта; цепочка «клиент → сегмент → рекомендация/кампания → первое подтверждённое действие» должна прослеживаться (FAQ В-4).
- Конверсия = подтверждённое событие в окне атрибуции после контакта; окно настраиваемое, по умолчанию 14 дней. Контрольная группа опциональна (процент настраивается, в т.ч. 0), но архитектура не мешает A/B (FAQ В-5).
- Прямой конкурент из рекомендаций не исключается, а получает понижающий коэффициент (FAQ В-7). Для гостей без истории — fallback по популярности (FAQ В-10).
- Масштаб (допущение команды, заказчик не задаёт): 80–150 арендаторов, ~40 000 посетителей в месяц, файл до 100 тыс. строк.
- Внешние каналы рассылки (SMS/пуш/email-провайдеры) вне системы: мы отдаём CSV и API, сами не отправляем. Лимит частоты контактов заказчиком не задан и настраивается на уровне кампаний/каналов (FAQ В-9).
- Кабинет арендатора в полном виде не нужен; R-3 остаётся как разграничение прав (FAQ В-6).

**0.4. Стек.**

- **Backend:** Go, слои `handler → service → repository`, интерфейсы на границах, REST, горутины для импорта и пересчёта сегментов (воркеры + очередь).
- **Frontend:** React + TypeScript SPA (`apps/web`), общение с backend только через REST (`/api/v1`).
- **Монорепозиторий:** Bun workspaces + Turborepo; Go-модуль один, в `apps/api`. Правила структуры кода — `docs/ARCHITECTURE.md`.
- **БД:** SQLite на старте, миграция на PostgreSQL без переделки модели; 3НФ; миграции goose.
- **Принципы:** SOLID, чистая архитектура, слабая связность, расширяемость через справочники и контракты.

### 3. Сквозные правила

1. **Единые идентификаторы** (`R-*`, `E-*`, `UC-*`, `US-*`, `C-*`, эндпоинты `METHOD /path`); объект везде называется одинаково (глоссарий: русское имя + имя в коде).

4. **Диаграммы не перегружать:** ≤ ~15 узлов, иначе разбить.
5. **Изоляция арендатора** (R-3): во всех артефактах (CRUD, sequence, API, C4) явно показать, что арендатор видит только свои агрегаты и не имеет доступа к данным других арендаторов ни в UI, ни через API (проверка на уровне service + фильтр в repository).
